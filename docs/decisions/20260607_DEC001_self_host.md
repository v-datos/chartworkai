# DEC-001 — Self-host: manage the framework's productization with the framework

**Date:** 2026-06-07
**Authority:** Orchestrator
**Status:** Decided

## Context

The framework needs to be productized (made project-agnostic and sellable). It claims to run "any complex, long-lived multi-agent project." The cleanest way to (a) test that claim and (b) produce a disciplined backlog is to run the framework on its own productization.

Options considered:
- **A. Manage productization ad hoc** (issues/notes only). Rejected — exactly the chat-drift the framework exists to prevent.
- **B. Dogfood — install the framework's operating artifacts on the framework repo and run it.** Chosen.

## Ruling

Install the framework's canonical operating artifacts at the framework repo root and manage the productization through them: `PROJECT_CHARTER.md`, `AGENTS.md`, `STATUS.md`, `TASKS.md`, `docs/phase_plan.md`, `docs/decisions/`, `docs/handoffs/`, `docs/domain/`, and (repurposed) `docs/data/`.

## Rationale

Dogfooding is the strongest possible agnosticism test: the framework repo is a **methodology / docs / shell** project, not data-science — so installing on itself immediately exercises the non-data-science path we are trying to make first-class. It also yields a structured, auditable backlog for the work.

## Implementation notes

- The bootstrap script was **not** used (it targets external dirs and would create redundant `_framework_*` copies inside the framework). Artifacts were authored directly from the framework's own templates.
- Roles were renamed for the domain (Framework Architect, Template & Docs Engineer, Dogfood & Compliance QA) per the framework's "rename roles" principle.

## Consequences per agent

- **Orchestrator:** maintains charter/phase_plan/STATUS/TASKS for this project.
- **Dogfood & Compliance QA:** the framework must pass its own checks at each phase close.
- **All:** we live with our own rituals; if they hurt here, that is a finding to fix.
